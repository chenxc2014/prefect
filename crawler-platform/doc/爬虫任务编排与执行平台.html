01 / 实施原则目标与实施边界

最终交付：现有网站采集能力持续可用；同一服务器能安全执行多个独立任务；多台 Linux/Windows 服务器由统一平台管理；网站可绑定服务器，也可在符合条件的节点间分配；出现故障能够定位、核对与恢复。

首期必须完成

  • 旧类式入口和旧函数式入口的完整接入。
  • 下载、验证码、截图、日志、浏览器会话隔离。
  • 任务路由、账号互斥、业务防重、状态回写。
  • Linux/Windows 节点、监控与发布回退。
  • 代表性网站迁移 Linux 并核对数据等价性。

后续逐步完善

  • Linux 单任务容器、按需扩容。
  • 网站分析、定位取证与受约束代码生成。
  • 页面变化检测、采集方案推荐。
  • 大规模节点和控制中心高可用。
保留约定：DataDownloadXXX 的构造参数、login/fetch/fetchRK/fetchKC、已有业务公共方法继续沿用。CommonImports、CommonCheckCode 等模块只允许为经验证的隔离或跨平台问题作最小修改，并配兼容回归；不进行整体重写。
两个验收口径分开：“旧功能能被新平台执行”通过 Windows 兼容节点首先保证；“旧源码在 Linux 运行”需要迁移和逐站验证。多机执行不等于控制中心高可用，多进程也不等于文件或桌面已隔离。

本页中的部署片段用于形成可执行的实施基线；标注“待开发”的工程接口不是现有功能。命令先在测试环境按冻结版本验证，再进入生产。

一次任务如何流转

  1. 开发与发布：在工作区修改、验证代码，再将执行代码发布到需要运行它的节点。修改工作区文件不会自动更新服务器，登记 Prefect 部署也不会自动复制代码。
  2. 提交运行：开发者从浏览器或 API 向 169 创建运行；后续也可由控制中心按已配置的调度计划创建运行。当前已有两个测试部署：crawler-dev-probe/linux-169 与 crawler-dev-probe/windows-167。
  3. 按队列领取：Linux 部署进入 dev-linux / node-169，由 169 Worker 领取；Windows 部署进入 dev-windows / node-167，由 167 Worker 领取。Worker 主动访问控制 API，无需开发机逐次通过 SSH 启动任务。
  4. 在节点执行：被选中的 Worker 启动任务进程，执行本机已发布代码。当前合成验证还通过独立子进程验证超时回收与目录隔离；真实爬虫接入后，登录、查询、下载及后处理也应在该执行节点完成。
  5. 状态回传：运行状态和配置上报的日志回到 169，在同一个中文管理界面查看；下载文件仍保存在执行节点。后续需另行实现统一产物上传、业务入库及结果对账。
例子：在开发机浏览器点击 Windows 测试部署的“运行”，请求先到 169，再由 167 Worker 领取并在 167 生成文件。169 负责记录和展示结果，文件不会因此自动复制到 169 或开发机。Linux 测试部署则在 169 本机执行。

05 / 分配规则节点、队列与并发控制

首期采用两个 Process 工作池：linux-process、windows-process。每个池按网络区域、执行能力和固定主机划分队列。不要仅用 Worker 名称实现主机绑定。

队列示例允许订阅的节点用途
linux-process / general-zone-aLinux zone-a 且具备任务所需浏览器与网络能力的节点通用任务共享；按相同能力扩容。
linux-process / node-linux-01仅 linux-01指定出口、专用软件、原范围绑定。
windows-process / node-win-01仅 win-01现有 crawl_code 范围的兼容执行。
windows-process / desktop-win-01-s1仅 win-01 的指定交互会话鼠标/键盘/桌面截图任务；首期队列并发为 1。
订阅规则必须显式：Worker 使用 --work-queue 指定队列；省略队列会订阅池内全部队列，可能破坏固定范围和桌面会话隔离。两个 Worker 的 --limit 不会自动形成整机总上限；多 Worker 时还需主机级信号量或合理分配额度。

路由算法（自研模块）

  1. 查站点注册表，判定入口、OS、浏览器、网络区域、桌面需求。
  2. 若有固定主机要求，查专用队列；无可用主机则排队/告警，不自动跨范围执行。
  3. 无固定要求时，选择能满足全部能力的共享队列；Linux-ready 任务优先进入 Linux 池。
  4. 进入执行前获取账号互斥与必要站点并发额度；无法获取则有界等待或重新排队，不占着全部浏览器资源空等。
  5. 记录 routing_reason、node_id、能力快照和规则版本，便于解释“为什么在这台机运行”。

并发锁由所有新执行节点共同遵守；迁移窗口中，未接入新锁的旧执行器通过网站/账号所有权排除，不能认为新锁会自动约束旧程序。锁需有租约与续约；续约失败时执行器停止启动新副作用步骤，并进入核对，避免锁过期后双执行。

领取 → 投递 → 执行的完整过程

  1. 桥接按 ownership 读取允许迁移的业务范围。原程序对同范围必须停止领取；读取存储过程是否有副作用须先核实。
  2. 事务内使用条件更新/行锁领取源任务，写入 crawl_job 与 outbox。现有 ISCL 的含义由实际流程映射，不能直接照搬为“已成功”。
  3. 投递器读取 outbox，以稳定幂等键调用所选版本 Prefect 的创建运行接口，记录 flow_run_id。网络超时后先核对投递结果，再重试。
  4. 执行器二次检查任务终态和有效租约，获取资源锁，创建 attempt 与隔离目录；重复运行拿不到有效租约即退出，不进行业务写入。
  5. 执行完整旧链路；下载与后处理生成 manifest/receipt；更新业务结果，并确认平台状态。
  6. 对账器周期检查“源任务已领但未投递”“运行结束但业务未回写”“失联但可能仍有子进程”等情况，分类恢复。
投递和副作用都要幂等：数据库事务无法与远程 API 形成天然原子事务。outbox 解决可恢复投递；唯一业务键、有效执行租约、导入回执解决重复执行。不能承诺调度层提供业务“恰好一次”。

状态与错误分类

待领取 → 已领取 → 已投递 → 执行中 → 已采集 → 已校验 → 处理中 → 已完成；异常分支为 等待重试 / 待人工处理 / 已取消 / 结果未确认。状态必须带阶段和尝试号；“已采集”不等于“已完成”。

情况建议策略业务确认

下面两个 Python 文件是独立冒烟样例，不依赖旧爬虫。它们用于验证 API、认证、代码可见性、队列绑定和单机并发。所有目标节点先部署相同代码；路径按操作系统分别注册，避免 Linux 路径交给 Windows。

flows/smoke.py · 现代 Python 环境
import os
import platform
import socket
import time
from datetime import datetime, timezone
from pathlib import Path
from uuid import uuid4

from prefect import flow, get_run_logger


@flow(name="crawler-smoke", retries=0)
def smoke(hold_seconds: int = 10) -> dict:
    if not 0 <= hold_seconds <= 120:
        raise ValueError("等待时长必须在 0 到 120 秒之间")
    root = Path(os.environ["CRAWLER_RUN_ROOT"])
    run_dir = root / "smoke" / str(uuid4())
    run_dir.mkdir(parents=True, exist_ok=False)
    started = datetime.now(timezone.utc).isoformat()
    (run_dir / "probe.txt").write_text(started, encoding="utf-8")
    get_run_logger().info("节点=%s，进程=%s", socket.gethostname(), os.getpid())
    time.sleep(hold_seconds)
    return {
        "hostname": socket.gethostname(),
        "os": platform.system(),
        "pid": os.getpid(),
        "started_at": started,
        "finished_at": datetime.now(timezone.utc).isoformat(),
        "run_dir": str(run_dir),
    }

灰度切换的操作顺序

  1. 选择固定网站/账号范围，备份现有配置、任务领取范围和对应代码，保留回退版本。
  2. 将该范围设为“切换中”：停止旧程序领取新任务，但允许已运行任务结束。原有 crawl_code 过滤如何实现，必须以存储过程实际能力为准。
  3. 核对旧任务、浏览器、文件后处理、导入批次全部终结；不能只看旧队列为空。
  4. 原子切换 ownership 到新平台，记录切换时间与范围，再启用新桥接。
  5. 从 1 个站点/账号开始，扩大到一组，再到该范围全量；以成功率、数据一致性、耗时和异常情况作为门槛。
  6. 每次扩大前完成未确认任务核对。试点稳定后复制到其他节点，不同时迁移所有站点和全部运行环境。

17 / 回退方案上线异常与故障处理

灰度范围回退步骤

  1. 停止桥接向异常范围创建新运行，暂停对应专用业务队列；共享队列按站点路由关闭，避免影响其他任务。
  2. 列出运行中/已采集/处理中任务，优先排空；必须取消时先完成所属进程树终止确认。
  3. 核对源系统、outbox、外部上传与导入回执。对结果未确认的任务先查实际数据，不能一律把 ISCL 改回 0。
  4. 确认新平台不再持有该范围的有效执行租约，更新 ownership 到旧系统；只重放确认未完成的业务请求。
  5. 恢复旧领取范围和已冻结版本，执行一个小样本核对，再恢复正常调度。
  6. 保留新运行日志和产物，记录问题范围与根因；无需删除新平台数据库或运行目录。
故障第一动作恢复要点
控制中心不可用桥接停止新投递；节点不擅自重复获取任务。核对仍在运行的子进程与产物；控制恢复后先对账再放量。
某节点失联隔离节点分配，保留业务任务状态。确认旧执行已停止或输出已被隔离；再以新 attempt 重派到同能力节点。
站点布局改变暂停该站点自动重试，保留截图/DOM/网络证据。在测试环境修复定位并回归，发布新版本；其他站点继续运行。
新版本数据异常停止该版本新任务，暂缓产物导入。新任务路由回上一版本；已入库数据按业务批次处理，不自动删库。
控制数据库升级不兼容停止升级后的投递。用备份恢复匹配旧版本的新实例并核对外部副作用；不能直接启动旧镜像连接已升级数据库。
